# Besik: список задач для развития интернет-магазина

Дата: 12 октября 2026 года.

Это план работ по текущему frontend и документу ENDPOINTS.md. Backend, инфраструктура и работа опубликованного магазина не проверены. Предлагаемые ниже API и модели данных нужно реализовать или сверить с фактическим backend; они не считаются уже существующими.

## Как использовать список

- **P0:** основа безопасного запуска и полного процесса покупки.
- **P1:** удобство клиента, работа поддержки, производительность и привлечение через поиск.
- **P2:** развитие после запуска и проверки спроса.
- **FE:** frontend; **BE:** backend; **OPS:** сотрудники магазина и инфраструктура.
- Каждый раздел с ID можно превратить в отдельную задачу. Чекбоксы — её подзадачи. Критерий готовности нужно проверить перед закрытием задачи.
- Приоритеты — предложение. Сроки и стоимость не оценены: для оценки нужны состояние backend, команда, объём каталога и бизнес-правила магазина.

## Исходное состояние

Уже реализованы адаптивная витрина, категории, поиск, сортировка, фильтр наличия, RU/EN/KA, галерея фотографий, избранное, корзина в localStorage, гостевой заказ, повторная проверка цен и остатков, обработка ошибок и подтверждение номера заказа. Демо загружается отдельным модулем. Для изображений уже используется lazy loading, для главного баннера — высокий приоритет загрузки.

Проверки 12 октября 2026 года: production-сборка успешна, существующие 16 тестов бизнес-логики успешны. Основной JS: 305,32 КБ, gzip 93,79 КБ; CSS: 25,47 КБ, gzip 6,38 КБ; отдельный demo JS: 7,58 КБ, gzip 3,17 КБ. Это размеры сборки Vite, а не измерение времени загрузки, серверного сжатия или Core Web Vitals. Фотографии, шрифты и API-ответы в эти значения не входят.

Основные ограничения: нет пользовательской авторизации и онлайн-оплаты; доставка включается в итог после создания заказа; нет истории заказов, кабинета и системы обращений; каталог фильтруется на клиенте; фотографии вариантов запрашиваются отдельными запросами. В документированном API авторизация отсутствует. Проверять защищённость реального сервера нужно отдельно.

## 1. Бизнес-правила и защита API

### BASE-01 — Зафиксировать правила покупки и обслуживания [P0 · FE/BE/OPS]

- [ ] Определить способы оплаты: онлайн, при получении, перевод; реализовывать только поддерживаемые магазином варианты.
- [ ] Определить зоны доставки, тарифы, сроки, условия бесплатной доставки и ограничения товаров.
- [ ] Указать точки самовывоза, адреса, график и срок хранения заказа.
- [ ] Утвердить правила отмены, возврата, гарантий и возврата денег; определить ответственного сотрудника.
- [ ] Выбрать рабочие часы поддержки, канал оповещения оператора и целевое время первого ответа.
- [ ] Зафиксировать правила публикации товаров. Сейчас активные варианты показываются и у товаров draft; это существующее поведение, менять его нужно осознанно.

**Готово, когда:** тарифы, способы оплаты, статусы и обязанности сотрудников описаны и одинаково используются в интерфейсе и серверной логике.

### BASE-02 — Разделить публичный API, клиентский кабинет и управление магазином [P0 · BE]

- [ ] Оставить публичными только нужные витрине операции и проверяемое гостевое оформление.
- [ ] Защитить изменение товаров, склада, платежей и служебных статусов; задать роли клиента, поддержки и администратора.
- [ ] Проверять владельца каждого заказа, обращения и файла на сервере при каждом чтении и изменении.
- [ ] Брать customerId авторизованного заказа из сессии, а не доверять идентификатору, присланному клиентом.
- [ ] Ограничить частоту чувствительных запросов: вход, коды подтверждения, гостевое оформление, обращения.
- [ ] Писать журнал действий сотрудников с заказами и платежами, исключая секреты из логов.

**Готово, когда:** клиент не может получить чужой заказ, подменить владельца, изменить цену, остаток или статус платежа; оператор получает только разрешённые права.

## 2. Авторизация через сторонние сервисы и личный кабинет

### AUTH-01 — Реализовать пользовательскую сессию [P0 · FE/BE]

- [ ] Добавить модель пользователя и отдельную связь с внешним аккаунтом: provider + уникальный идентификатор пользователя у провайдера.
- [ ] Реализовать создание сессии, получение текущего пользователя, выход и истечение сессии.
- [ ] Для обычного web-сценария использовать серверную сессию с HttpOnly/Secure cookie; подобрать SameSite под размещение сайта и API, добавить необходимую защиту от CSRF.
- [ ] Не сохранять долгоживущие секреты авторизации в localStorage; локальные корзина и язык могут продолжать использовать localStorage.
- [ ] Добавить состояния загрузки входа, гостя, авторизованного пользователя и истёкшей сессии без потери корзины.

**Готово, когда:** вход сохраняется после обновления страницы, выход прекращает доступ к кабинету, истёкшая сессия не уничтожает гостевую корзину.

### AUTH-02 — Добавить вход через Google [P0 · FE/BE]

- [ ] Зарегистрировать приложение у провайдера и настроить разрешённые адреса сайта и callback для dev и production.
- [ ] Добавить кнопку входа и обработку отказа пользователя, закрытия окна и ошибки провайдера.
- [ ] Выбрать поддерживаемый сценарий Google Identity Services; сервер должен проверять результат входа, включая подпись, issuer, audience и срок действия.
- [ ] Использовать идентификатор sub для связи с аккаунтом Google; не использовать email как неизменяемый ID.
- [ ] Если применяется OAuth authorization code flow, использовать защиту потока по актуальным рекомендациям: PKCE S256 и проверку параметров state/nonce согласно выбранному протоколу.
- [ ] После первого входа запросить недостающие контактные данные отдельно: вход через Google не гарантирует наличие телефона для доставки.

**Готово, когда:** новый клиент получает один аккаунт, повторный вход возвращает тот же аккаунт, поддельный или просроченный результат входа отклоняется сервером.

Основание: [проверка Google ID token](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [OAuth Security BCP — RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html).

### AUTH-03 — Связывание аккаунтов и резервный способ входа [P1 · FE/BE]

- [ ] Выбрать дополнительные провайдеры по аудитории магазина: например, Apple или Facebook; перед реализацией проверить требования каждого сервиса.
- [ ] Подключать новый способ входа из уже подтверждённого аккаунта.
- [ ] Не объединять аккаунты автоматически только потому, что совпал email; требовать подтверждение владения.
- [ ] Добавить резервный вход по подтверждённому email или телефону, если он нужен бизнесу.
- [ ] Запретить отключение последнего доступного способа входа без замены.
- [ ] Определить процедуру восстановления доступа, блокировки и удаления аккаунта.

**Готово, когда:** клиент не теряет историю при добавлении провайдера, а чужой аккаунт нельзя присоединить по одному совпадению контактных данных.

### AUTH-04 — Профиль клиента, адреса и настройки [P1 · FE/BE]

- [ ] Создать разделы «Профиль», «Адреса», «Заказы», «Обращения», «Настройки уведомлений».
- [ ] Разрешить изменение имени, телефона и email с подтверждением чувствительных изменений.
- [ ] Добавить несколько адресов, адрес по умолчанию и выбор сохранённого адреса при покупке.
- [ ] Хранить предпочтительный язык и допустимые каналы уведомлений.
- [ ] Подставлять данные в оформление, сохраняя возможность изменить получателя конкретного заказа.

**Готово, когда:** повторный заказ можно оформить с сохранёнными данными, а изменение профиля не переписывает данные старых заказов.

### AUTH-05 — Синхронизация корзины и избранного после входа [P1 · FE/BE]

- [ ] Добавить хранение корзины и избранного для авторизованного пользователя на сервере.
- [ ] Определить правила объединения локальной и серверной корзин, одинаковых вариантов и количества.
- [ ] Повторно проверить доступность и цену объединённых позиций; объяснить ограничения клиенту.
- [ ] Синхронизировать состояние между устройствами и корректно разделять данные разных пользователей на одном устройстве.
- [ ] Сохранять гостевой сценарий покупки без требования регистрации.

**Готово, когда:** вход не теряет выбранные товары, выход не раскрывает корзину предыдущего пользователя следующему.

## 3. Оформление, оплата и устойчивость заказов

### CHECKOUT-01 — Рассчитывать доставку и полную сумму заранее [P0 · FE/BE]

- [ ] Добавить API предварительного расчёта товаров, доставки и итоговой суммы.
- [ ] Передавать адрес или зону, выбранный способ получения и состав корзины; цены вычислять на сервере.
- [ ] Показывать итог до кнопки подтверждения, включая стоимость доставки и предполагаемый срок.
- [ ] Пересчитывать при изменении корзины или адреса; не позволять использовать просроченный расчёт без проверки.
- [ ] Показывать выбранную точку самовывоза, адрес и часы работы.
- [ ] Сохранять существующее подтверждение клиентом изменившихся цен.

**Готово, когда:** клиент видит полную сумму до отправки заказа; если условия изменились, приложение объясняет изменения и запрашивает повторное подтверждение.

### CHECKOUT-02 — Подключить оплату [P0 · FE/BE/OPS]

- [ ] Выбрать платёжного провайдера с учётом договора магазина, валюты GEL, методов оплаты и возвратов.
- [ ] Создавать платёжную сессию на сервере по заказу; использовать защищённый интерфейс провайдера.
- [ ] Реализовать страницы результата: успешно, ожидается подтверждение, ошибка, отмена.
- [ ] Подтверждать оплату на сервере через проверенный webhook или иной предусмотренный провайдером серверный механизм.
- [ ] Обрабатывать повторные и пришедшие не по порядку события; не считать redirect в браузере доказательством оплаты.
- [ ] Разрешить повторную попытку оплаты без создания нового заказа и второго успешного списания.
- [ ] Реализовать разрешённую сотруднику операцию возврата денег и её отображение клиенту.

**Готово, когда:** тестовые сценарии оплаты, отказа, отмены и возврата проходят; сумма соответствует серверному заказу; браузер не может сам установить paid.

### CHECKOUT-03 — Исключить дубли заказов при повторной отправке [P0 · FE/BE]

- [ ] Выдавать ключ операции для попытки оформления и реализовать серверную идемпотентность.
- [ ] При повторе той же операции возвращать ранее созданный заказ; при изменении состава не переиспользовать ключ молча.
- [ ] После timeout получать результат операции и показывать созданный заказ либо безопасный повтор.
- [ ] Сохранять введённые данные и корзину при ошибке; очищать корзину после подтверждённого создания.
- [ ] Протестировать потерю ответа, повторный клик, обновление страницы и две вкладки.

**Готово, когда:** несколько повторов одной операции создают один заказ, и клиент может восстановить результат после разрыва связи.

### CHECKOUT-04 — Согласовать резервирование остатков с заказом [P0 · BE/FE]

- [ ] Проверить фактическую серверную связь создания заказа, резервов и оплаты; наличие endpoint резервирования само по себе её не доказывает.
- [ ] Определить момент резерва и его срок; выдавать понятную ошибку при недостатке товара.
- [ ] Обеспечить атомарность проверки и резерва, если несколько клиентов покупают последний товар.
- [ ] Освобождать резерв при допустимой отмене или истечении срока и списывать его при нужном этапе исполнения.
- [ ] Отображать исчерпание товара и срок неоплаченного заказа без обещания недоступного остатка.

**Готово, когда:** последний экземпляр не продаётся одновременно двум клиентам, а брошенные заказы не блокируют остаток бессрочно.

## 4. История заказов и статусы у клиента

### ORDER-01 — Определить модель статусов и правила переходов [P0 · BE/FE/OPS]

- [ ] Сопоставить существующие pending, awaiting_payment, paid, processing, shipped, completed, cancelled, payment_failed с понятными названиями на RU/EN/KA.
- [ ] Описать допустимые переходы для доставки, самовывоза и каждого способа оплаты.
- [ ] Разделить состояние оплаты и исполнения заказа в модели/представлении: «оплачен» и «отправлен» описывают разные события.
- [ ] Определить отображение возвратов и частичных возвратов; добавить недостающие поля или статусы backend.
- [ ] Хранить историю изменений со временем и инициатором; отображать клиенту только нужные события.
- [ ] Задать серверные ограничения на отмену, повторную оплату и возврат.

**Готово, когда:** клиент и оператор одинаково понимают состояние заказа, недопустимые переходы отклоняются сервером.

### ORDER-02 — Создать список заказов клиента [P0 · FE/BE]

- [ ] Добавить защищённое получение собственных заказов с серверной пагинацией; не отдавать общий GET /orders в клиентский кабинет.
- [ ] Показать номер, дату, сумму, статус исполнения, состояние оплаты и миниатюры позиций.
- [ ] Добавить фильтрацию по состоянию и поиск по собственному номеру заказа.
- [ ] Реализовать состояния загрузки, отсутствия заказов, ошибки и истёкшей сессии.
- [ ] Сохранять историю независимо от браузера и localStorage.

**Готово, когда:** клиент видит только свои заказы с любого устройства; список большой истории не требует загрузки всех записей.

### ORDER-03 — Создать страницу отдельного заказа [P0 · FE/BE]

- [ ] Показывать позиции, количество, цены на момент покупки, доставку, скидки при их наличии и итог.
- [ ] Использовать сохранённые snapshot-данные, чтобы изменение каталога не меняло старый заказ.
- [ ] Показать адрес или точку самовывоза, получателя, сроки, историю статусов, трек-номер при наличии.
- [ ] Добавить действия «Оплатить», «Повторить заказ», «Связаться с поддержкой», «Запросить отмену/возврат» по правилам сервера.
- [ ] При повторном заказе проверять текущие цены, доступность и существование вариантов.
- [ ] Показывать документы заказа, если магазин их выдаёт.

**Готово, когда:** клиент понимает состав и состояние покупки, видит доступные действия и может обратиться по конкретному заказу.

### ORDER-04 — Предоставить гостю доступ к заказу [P0 · FE/BE]

- [ ] Собирать и подтверждать нужный контакт для выбранного канала доступа.
- [ ] Реализовать доступ через подтверждение контакта или ограниченную защищённую ссылку с подходящим сроком действия.
- [ ] Не открывать персональные данные по одному номеру заказа или перебираемому ID.
- [ ] После входа позволить присоединить гостевые заказы только после доказательства владения контактом.
- [ ] Ограничить попытки подтверждения, срок и повторное использование кодов.

**Готово, когда:** гостевая покупка остаётся доступной без регистрации, а посторонний не может получить её данные по известному номеру.

### ORDER-05 — Отмена и возвраты [P1 · FE/BE/OPS]

- [ ] Добавить запрос на отмену в разрешённых состояниях и явно показывать, когда отмена требует согласования.
- [ ] Создать заявку на возврат с выбором позиций, количества, причины и подтверждающих файлов при необходимости.
- [ ] Отображать этапы рассмотрения, инструкции по передаче товара и состояние возврата денег.
- [ ] Согласовать финансовое действие с платёжным провайдером и отдельный учёт возврата товара на склад.
- [ ] Зафиксировать условия для частичного возврата и расходов на доставку.

**Готово, когда:** клиент видит результат заявки, а возврат денег и складское движение не подменяют друг друга.

## 5. Поддержка покупателей

### SUPPORT-01 — Создать единый вход в поддержку и систему обращений [P0 · FE/BE/OPS]

- [ ] Добавить заметный пункт «Поддержка» и доступ из страницы заказа и ошибки оформления.
- [ ] Публиковать контакты, рабочие часы и ожидаемое время ответа.
- [ ] Создать форму обращения: тема, сообщение, связанный заказ, обратный контакт для гостя.
- [ ] Выдавать номер обращения и хранить переписку на сервере.
- [ ] Защитить обращения от спама, подмены владельца и утечки чужой переписки.
- [ ] Обеспечить поступление обращения в рабочую очередь сотрудников; email или мессенджер может быть дополнительным каналом уведомления.

**Готово, когда:** клиент может отправить обращение, получить подтверждение и ответ, а сотрудник видит обращение и контекст заказа.

Первый выпуск: обращения с сохраняемой перепиской. Чат в реальном времени можно добавить позже, когда есть сотрудники и понятный режим обслуживания.

### SUPPORT-02 — Раздел «Мои обращения» [P1 · FE/BE]

**Готово, когда:** критические действия проходят на staging с интеграциями тестового режима, ошибки воспроизводимы и не теряют данные.

### OBSERVE-01 — Аналитика, ошибки и доступность [P1 · FE/BE/OPS]

- [ ] Собирать события просмотра, поиска, корзины, начала оформления, подтверждённой покупки и отказов без персональных данных в параметрах.
- [ ] Подтверждённую покупку учитывать по серверному событию оплаты/принятия заказа согласно бизнес-модели, исключая дубли.
- [ ] Собирать ошибки frontend и API с корреляцией запросов и безопасными логами.
- [ ] Измерять конверсию этапов, ошибки оплаты, время ответа поддержки и скорость страниц.
- [ ] Настроить уведомления о сбоях заказа/оплаты, очередей и мониторинг доступности.
- [ ] Согласовать правила cookie, согласий и маркетингового трекинга по требованиям магазина.

**Готово, когда:** видно, где клиент не завершил покупку или не получил ответ, а оператор получает сигнал о реальной проблеме.

### RELEASE-01 — Подготовить публикацию и восстановление [P0 · FE/BE/OPS]

- [ ] Подготовить staging и production с HTTPS, корректными API URL, CORS, cookie и callback провайдеров.
- [ ] Настроить обслуживание маршрутов публичных страниц и приватного кабинета без ошибок при обновлении.
- [ ] Хранить серверные секреты вне VITE_* и публичной сборки.
- [ ] Настроить резервные копии данных, проверить восстановление и безопасный откат версии.
- [ ] Проверить платежные callback/webhook, отправку уведомлений и реальные контакты поддержки.
- [ ] Назначить сотрудников на обработку заказов, резервов, возвратов и обращений.

**Готово, когда:** тестовый заказ проходит весь путь до получения и ответа поддержки; магазин можно восстановить после сбоя.

## 10. Предлагаемые изменения API

Названия примерные: конечный контракт согласуется с backend. Все ответы используют существующие строковые BIGINT ID и точные серверные значения денежных сумм. Не использовать JS float как источник финансовой истины.

- **Сессии:** текущий пользователь, начало/завершение внешнего входа, выход и управление способами входа. Например GET /auth/me, POST /auth/logout и callback выбранного провайдера.
- **Кабинет:** профиль, адреса, корзина и избранное; например /me/profile, /me/addresses, /me/cart, /me/favorites.
- **Витрина:** GET /storefront/catalog с поиском/фильтрами/пагинацией и preview URL; отдельная выдача подробностей и галереи.
- **Оформление:** POST /checkout/quote, идемпотентное создание заказа, восстановление результата операции после timeout.
- **Клиентские заказы:** GET /me/orders и GET /me/orders/:id, история событий, разрешённые действия и серверная проверка владельца.
- **Гостевой доступ:** запрос и подтверждение кода/ссылки с ограничениями; привязка заказа после подтверждения владения.
- **Платежи:** серверное создание сессии, получение результата и webhook провайдера; клиент не меняет payment.status напрямую.
- **Поддержка:** обращения, сообщения, вложения и операторские действия с проверкой прав.
- **Возвраты:** заявки по позициям заказа, обработка сотрудником, финансовое действие и события результата.

Предлагаемые сущности: пользователь, внешняя идентичность, сессия, адрес, история статусов заказа, обращение, сообщение обращения, вложение, заявка на возврат, событие уведомления, ключ операции оформления. Часть заказа/платежа уже есть в backend по документации; дополнять существующую модель, а не дублировать её без причины.

## 11. Порядок выполнения и зависимости

1. **Правила и исходные измерения:** BASE-01, проверка BASE-02, PERF-01. Получить фактический контракт backend, тарифы, провайдеров и ответственных сотрудников.
2. **Основа доступа:** BASE-02, AUTH-01, AUTH-02. После этого можно безопасно строить кабинет и операторские экраны. Поддержку гостя можно делать параллельно с подготовкой входа.
3. **Полная покупка:** CHECKOUT-01–04, ORDER-01, ORDER-04, NOTIFY-01, CONTENT-01. Сначала серверные гарантии и расчёт, затем интерфейс и интеграции.
4. **История и обслуживаемая поддержка:** ORDER-02–03, SUPPORT-01, SUPPORT-03, затем SUPPORT-02 и AUTH-04. Рабочая очередь сотрудника входит в первый выпуск поддержки.
5. **Оптимизация и обнаружение товаров:** PERF-02–08, CATALOG-01–03, AUTH-05, OBSERVE-01. Быстрые локальные улучшения PERF-03/04 можно выполнять раньше, после исходного замера.
6. **Возвраты и дополнительные способы входа:** ORDER-05, SUPPORT-04, AUTH-03; базовые условия возврата должны быть опубликованы уже при запуске.
7. **Развитие по данным:** SUPPORT-05, GROWTH-01.
8. **Перед каждым выпуском:** нужные проверки QUALITY-01; перед публичным запуском — RELEASE-01.

Зависимости, которые нельзя заменить одним frontend: проверка владельца заказа, внешняя авторизация, серверная сумма, платёжный webhook, идемпотентность, резерв товара, приватные вложения, надёжная очередь уведомлений и синхронизация между устройствами.

## 12. Что нужно определить перед оценкой сроков

- Где размещаются frontend и backend и есть ли отдельная административная панель.
- Сколько вариантов сейчас и ожидается через год; размеры фотографий и частота обновления остатков.
- Платёжный договор, методы оплаты и реальные условия доставки/самовывоза.
- Какие сервисы входа нужны аудитории и нужен ли собственный резервный вход.
- Кто отвечает клиентам, в какое время и каким инструментом пользуется.
- Какие контакты собирать и подтверждать у гостя для заказов, поддержки и уведомлений.
- Планируемая нагрузка, целевые устройства и требования к индексации RU/EN/KA.

Это точки уточнения для реализации и оценки, они не препятствуют подготовке плана. Переход на другой frontend-фреймворк, собственный realtime-чат и сложная программа лояльности не являются обязательными первыми шагами.
